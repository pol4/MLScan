# 13. План поэтапного развёртывания

Документ описывает **уровни развёртывания MLScan**: от одного Python-скрипта с Docker до
промышленного контура. Каждый уровень **самодостаточен** (полностью работоспособен в своих
возможностях анализа) и **чётко аргументирован**; следующий уровень только добавляет возможности
и компоненты.

Практика: [`../deploy/README.md`](../deploy/README.md) (выбор уровня, установка, проверка),
[`../deploy/upgrade.md`](../deploy/upgrade.md) (переход N → N+1).

---

## 1. Принципы

1. **Самодостаточность.** На каждом уровне систему можно использовать «как есть»: она даёт
   корректный результат в рамках своих возможностей анализа. Незавершённость никогда не
   маскируется: если модуль не смог отработать (модель не загрузилась, нет библиотеки, таймаут),
   вердикт — `Inconclusive` с частичным результатом (проверка «покрытия» работает на всех уровнях).
2. **Монотонность сложности.** Компоненты добавляются постепенно: локальный инструмент →
   изолированная микро-ВМ на одном узле → сервисы, объектное хранилище и СУБД → UI и аудит →
   интеграции → эксплуатация.
3. **Совместимость вверх.** Переход на следующий уровень не ломает предыдущий: API, данные и
   формат находок не меняются; установка идемпотентна; evidence append-only.
4. **Единый анализ, разная инфраструктура.** Набор проверяемых форматов не зависит от уровня:
   адаптеры форматов — общий модуль [`../poc/formats.py`](../poc/formats.py), используемый и PoC,
   и сервисом тестирования.
5. **Понятная граница.** Для каждого уровня явно указано, чего он **не** даёт, — чтобы не
   ожидать от простого уровня свойств промышленного контура.

## 2. Уровни

### Уровень 0 — PoC (Python + Docker)

**Аргументация.** Большинство рисков (RCE при десериализации, опасные глобалы, внешние ссылки,
prompt-injection, утечки секретов, структурные аномалии) выявляются **статикой без исполнения**.
Поэтому первый уровень — один скрипт и Docker — уже даёт полезный результат и покрывает максимум
форматов; инфраструктура не нужна.

* **Возможности анализа:** статика L1 по всем форматам (pickle/torch/numpy, SafeTensors, ONNX,
  HDF5/Keras, GGUF, архивы и вложенные архивы, ноутбуки, скрипты, Dockerfile, HTML/SVG,
  Jinja-шаблоны, конфиги/карточки/токенизаторы, MCP-манифесты, датасеты, сжатые payload'ы);
  динамика L2 в Docker (`--network none`, RO-FS, лимиты) и поведение L3 для исполняемых форматов;
  отчёт Markdown/JSON; вердикт с учётом покрытия.
* **Требования:** Python 3.10+ (только stdlib) и Docker (для динамики).
* **Не даёт:** сильной изоляции (только Docker), хранения истории, API, UI, аудита.
* **Приёмка:** `bash deploy/verify.sh 0` — статика находит `A-01` в опасном pickle и `INJ-01`
  в GGUF chat_template; при `--static-only` вердикт `Inconclusive`.
* **Каталоги:** [`../poc/`](../poc).

### Уровень 1 — Изолированная песочница (микро-ВМ) на одном узле

**Аргументация.** Динамический анализ означает **исполнение недоверенного кода**, а «инертные»
форматы загружаются нативными движками, которые сами могут быть уязвимы. Значит, нужен барьер
сильнее контейнера: отдельное ядро (Kata microVM), сетевой запрет, honeypot, наблюдаемость.

* **Возможности анализа:** те же, но L2/L3 выполняются в микро-ВМ с полным набором ограничений;
  артефакт отдаётся песочнице сервером (не монтируется), окружение уничтожается после скана.
* **Требования:** Kubernetes на одном узле, RuntimeClass `kata` (или `gvisor`), реестр образов,
  образ песочницы `mlscan-sandbox`.
* **Не даёт:** HTTP API, хранение артефактов и истории, UI.
* **Приёмка:** `bash deploy/verify.sh 1` — есть namespace `mlscan-sandbox`, RuntimeClass `kata`,
  NetworkPolicy; red-team Job подтверждает изоляцию.
* **Каталоги:** [`../deploy/stage1/`](../deploy/stage1), [`../deploy/sandbox-image/`](../deploy/sandbox-image).

### Уровень 2 — Сервис тестирования (S3 + PostgreSQL)

**Аргументация.** Модели бывают очень большими (сотни ГБ) и их нужно принимать из CI/платформы
многократно. Значит: объектное хранилище с адресацией по содержимому (`sha256/<name>`,
дедупликация), метаданные в СУБД, приём потоком и оркестрация песочницы как сервис.

* **Возможности анализа:** всё из уровня 1, плюс приём по HTTP, вердикт и находки через API,
  история по `sha256`, локализация сообщений RU/EN, честное покрытие в вердикте.
* **Требования:** уровень 1 + Garage (S3) + PostgreSQL + реестр образов.
* **Не даёт:** скоринга/policy/evidence/UI (уровень 3), реестра/гейта (4), метрик/качества (5).
* **Приёмка:** `bash deploy/verify.sh 2` — `POST /scans/upload` опасного pickle даёт
  `Malicious`/`Dangerous`, безопасный safetensors — `Safe`; объект есть в S3, запись есть в БД.
* **Каталоги:** [`../deploy/v2/data/`](../deploy/v2/data), [`../deploy/v2/db/`](../deploy/v2/db),
  [`../deploy/stage2/`](../deploy/stage2).

### Уровень 3 — Аналитика, Policy Engine, Evidence и UI

**Аргументация.** Результат сканирования должен превращаться в **решение** и **доказательство**:
скоринг, политика (что блокировать/отправлять на разбор), неизменяемый журнал (hash-chain) и
интерфейс для аналитика с разграничением доступа.

* **Возможности:** скоринг и Policy Engine, append-only evidence (файл + зеркало в PostgreSQL),
  отчёты JSON/Markdown/SARIF, веб-UI: вход (пользователи/API-ключи/роли), переключатель языка,
  `/settings` — глобальный язык всей системы, баннер неполной проверки.
* **Требования:** уровни 1–2 + Ingress (Istio) для внешнего доступа + модуль локализации.
* **Не даёт:** интеграций в поставку (уровень 4) и эксплуатационного контура (уровень 5).
* **Приёмка:** `bash deploy/verify.sh 3` — аналитика видит сканы, evidence проверяется,
  страница входа доступна, вход и отчёты работают.
* **Каталоги:** [`../deploy/stage3/`](../deploy/stage3), [`../deploy/v2/auth/`](../deploy/v2/auth),
  [`../deploy/i18n/`](../deploy/i18n), [`../deploy/ingress/`](../deploy/ingress).

### Уровень 4 — Интеграции (реестр, CI-gate, SIEM, threat-intel)

**Аргументация.** Проверка имеет смысл, только если она **останавливает** опасную модель на пути
в прод. Значит, нужен гейт в CI, реестр проверенных артефактов и выгрузка событий в SIEM.

* **Возможности:** реестр моделей по SHA-256, `POST /gate` с решением allow/block/review и
  exit-code для CI, экспорт в SIEM (NDJSON/CEF), список наблюдений threat-intel.
* **Требования:** уровни 2–3.
* **Не даёт:** метрик качества, retest, retention/TTL, backup (уровень 5).
* **Приёмка:** `bash deploy/verify.sh 4` — `/gate` блокирует известный плохой хэш, реестр доступен.
* **Каталоги:** [`../deploy/stage4/`](../deploy/stage4).

### Уровень 5 — Промышленная эксплуатация

**Аргументация.** Долгая работа требует наблюдаемости (метрики/алерты), контроля качества
(TPR/FPR на golden-наборе), непрерывной перепроверки, управления хранением (TTL/карантин) и
восстановления (backup с проверкой).

* **Возможности:** метрики Prometheus, `/quality` (TPR/FPR), `/sla`, `/retest` по cron,
  red-team Job, `/alerts`, retention/TTL + карантин + tombstones, backup/restore с проверкой,
  PDB, аттестация.
* **Требования:** уровни 3–4 + lifecycle + backup.
* **Приёмка:** `bash deploy/verify.sh 5` — метрики отдаются, качество `TPR=1.0/FPR=0.0`,
  CronJob'ы retest/lifecycle/backup существуют; `--full` прогоняет корпус (141 образец).
* **Каталоги:** [`../deploy/stage5/`](../deploy/stage5), [`../deploy/v2/lifecycle/`](../deploy/v2/lifecycle),
  [`../deploy/v2/backup/`](../deploy/v2/backup).

## 4. Сквозные возможности (работают на всех уровнях)

* **Единый форматный анализ** — `poc/formats.py` (PoC и сервис используют один набор адаптеров).
* **Честный вердикт** — учёт полноты покрытия: `Inconclusive` + перечень непроверенного вместо
  ложного `Safe`.
* **Локализация RU/EN** — в PoC (`--lang`), в сервисах и в UI; глобальная настройка языка
  (`MLSCAN_LANG` при запуске + `POST /settings/language` для администратора, хранение в БД).
* **Синтетический корпус** — [`../tests/vulnerabilities/`](../tests/vulnerabilities):
  141 образец (87 с закладками + 54 безопасных, включая ~198 МБ), отчёт `REPORT.md`
  (`87/87 обнаружено, 0/54 ложных`).

---

## 4.1. Подтверждение на стенде

План проверен на чистом кластере в два прохода: **поэтапно 0 → 1 → 2 → 3 → 4 → 5** (с проверкой
каждого уровня) и **сразу на максимальный уровень** одной командой (`install.sh 5 --with-falco`).
Итог полной проверки: все критерии `[OK]`, синтетический корпус **87/87 обнаружено, 0 пропусков,
0/54 ложных**, качество `TPR=1.0/FPR=0.0`. Найденные при установке дефекты (демо-скан песочницы,
идемпотентность Garage, уровневая раскладка ingress и адрес K8s API, метрики качества, гонка
append-only, порт-форварды в `--full`) исправлены в коде развёртывания.

## 5. Что вне плана

* Репликация хранилищ между зонами и DR-регламент (в single-node контуре — внешние процедуры).
* OIDC/Keycloak и mTLS (сейчас — API-ключи и пользователи в БД; SSO между сервисами через
  cookie на общем домене).
* GPU-анализ и запуск моделей на GPU (отдельный пул узлов).
* Обфускация/детект «спящих» payload'ов, требующих конкретных данных для активации, — частично
  покрыто поведенческим этапом, полное покрытие требует fuzzing-контура (red-team Job — основа).
