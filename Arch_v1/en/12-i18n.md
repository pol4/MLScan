# 12. UI and message localisation (RU/EN)

[Русский](../12-i18n.md) | **English**

This document describes the i18n subsystem: the UI language switch, the global system language
setting, and the translation of service messages, findings and reports. Implementation —
[`deploy/i18n/i18n.py`](../../deploy/i18n/i18n.py).

## 1. What is localised

| Layer | What is translated |
|-------|--------------------|
| Analytics UI | every label: sign-in, dashboard, artifact card, reports, settings page |
| Service messages | errors and notices of testing / integrations / ops / ingest (including alerts) |
| Verdict reasons | `service_reason` ("Max severity …", "Dangerous constructs of level …") |
| Findings | titles and evidence (`A-01`, `EXEC-02`, `FMT-01`, `BD-01`, …), including historical records |
| Reports | Markdown, JSON and SARIF — in the language of the request |

**Canonical identifiers are not translated**: `verdict` values (`Malicious`, `Dangerous`,
`Needs review`, `Safe`, `Inconclusive`), `severity` (`critical/high/medium/low/info`),
`policy.action` (`block/quarantine/allow`) and `check_id`. The UI and API filter by them, CSS
classes are built from them and decisions are made on them — they are machine values.

## 2. Language resolution levels

Priority (higher overrides lower):

1. **Explicit request** — `?lang=ru|en` in the URL (if duplicated, the last value wins) or the
   `X-MLScan-Lang` header (API/CI).
2. **User preference** — the `mlscan_lang` cookie (host-only, set by the switch).
3. **Global system setting** — the `settings` table in PostgreSQL (key `language`).
4. **Startup value** — the `MLSCAN_LANG` environment variable (ConfigMap/Deployment, default `ru`).
5. **Browser `Accept-Language`** — last resort only: the system language must not be overridden
   by client language settings (otherwise the global setting would appear broken for
   English-language browsers).

Levels 4–5 satisfy the "globally for the whole system" requirement: all services return messages
in the selected language, and an administrator can change it on the fly (30 s cache).

## 3. UI language switch

Every page header shows `Language: RU | EN`. The link goes to `/lang?set=<code>&next=<current
page with lang replaced>`: the service sets the `mlscan_lang` cookie (host-only, one year, so it
works both via IP and via hostname) and returns the user to the **same** page, adding
`?lang=<code>` as a fallback — switching works even when cookies are blocked. Pages and API
responses are served with `Cache-Control: no-store`, so a language change does not stick in
the cache.

### Session expiry

The session is signed (`SESSION_SECRET`) and lives for 12 hours; the `mlscan_session` cookie is now
issued with `Max-Age`, so the browser drops it consistently. When a session expires in an open tab
the UI no longer stays silent: browser navigation is redirected to `/login?expired=1` ("Your session
has expired — please sign in again"), and a 401 from `/api/overview` or `/api/stats` immediately
takes the page to the sign-in screen. API clients still receive `401 {"error": "…"}`.

## 4. Global setting (administrator)

* **UI** — the `/settings` page (the header link is visible to the `admin` role): choose the system
  language and save (`POST /settings/language`).
* **API (ops)** — `GET /settings` (current global language, startup language, supported ones) and
  `POST /settings/language?lang=en` (`admin` role only).
* The value is stored in the `settings` table (`key='language'`) and created automatically; without
  a database the startup language is used. The change is written to `audit_log`.

Verification:

```bash
curl -H "Authorization: Bearer $ADMIN_KEY" http://<ops>/settings
curl -X POST -H "Authorization: Bearer $ADMIN_KEY" "http://<ops>/settings/language?lang=en"
```

## 5. How translation works

The module has two independent parts:

1. **The `CATALOG`** — keys such as `ui.overview`, `dash.upload`, `msg.scan_timeout` with `ru`/`en`
   values. Services call `t(key, lang, **fmt)`.
2. **The `_RULES`** — translation of "free-form" strings that services already returned as data:
   finding titles, verdict reasons, load errors. `tr(text, lang)` applies the rules, while
   `tr_list`/`tr_phrase` translate composite values (lists joined by `, ` and `; `, and
   "label: number" constructs).

This approach makes it possible to show **historical** records stored in the database and evidence
before i18n was introduced in English, with no data migration: translation happens at render time.

## 6. Deployment

The module is distributed as the `mlscan-i18n` ConfigMap into every `mlscan-*` namespace and
mounted at `/opt/i18n` (just like `mlscan-authz` → `/opt/auth`); services receive `MLSCAN_LANG`
from environment variables. The scripts `deploy/stage{2,3,4,5}/apply.sh` and
`deploy/v2/ingest/apply.sh` create the ConfigMap automatically.

```bash
kubectl -n mlscan-analytics create configmap mlscan-i18n \
  --from-file=i18n.py=deploy/i18n/i18n.py --dry-run=client -o yaml | kubectl apply -f -
kubectl -n mlscan-analytics rollout restart deploy/mlscan-analytics
```

## 7. Verification

```bash
# request language
curl -s "http://<analytics>/healthz"                      # -> {"language": "...", "languages": ["ru","en"]}
curl -s "http://<analytics>/?lang=en" | grep -o "Upload model"

# global setting
curl -X POST -H "Authorization: Bearer $ADMIN_KEY" "http://<ops>/settings/language?lang=en"
sleep 31                                                  # 30 s cache
curl -s -H "Authorization: Bearer $ADMIN_KEY" "http://<testing>/scans/<id>" | jq -r .reason
```
