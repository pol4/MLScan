# 03. Анализ ограничений архитектуры v2

Документ систематизирует **ограничения v2**, выявленные при эксплуатации и при проектировании
путей для артефактов 1 ТБ+, и формулирует требования к v3. Численные оценки — по фактам стенда
(см. `02-large-model-pipeline.md`, `tests/perf/garage_ingest_result.json`).

## 0. Кратко: что мешает масштабу 1 ТБ+

1. **Ёмкость/отказоустойчивость хранилища**: Garage — один узел, `replication_factor=1`, одна PVC;
   при 1 ТБ+ это единая точка отказа и отсутствие шардирования/DR (v2 задумана под сотни ГБ, не ТБ).
2. **Пропускная способность ingest**: single-node ingest ≈ **32–43 МБ/с** (замер), параллельные
   части дают лишь ~1.3×, т.е. 1 ТБ ≈ **6–9 часов** даже на канале ≥10 Гбит/с — канал не
   утилизируется, узкое место в узле/диске.
3. **Двухходовой путь и копии**: legacy-приём последует «клиент→сервис→Garage» с двойной записью
   диска; анализ крупных объектов требует **материализации** (полной загрузки) — для 1 ТБ невыполнимо,
   поэтому сейчас только статика по префиксу.
4. **Архивы 1 ТБ не поддерживаются end-to-end**: обход членов ограничен архивными лимитами
   (128 МиБ/архив) и не потоковый из S3 (нет range/членного стриминга, нет индексации).
5. **Динамика для ТБ невозможна**: лимиты песочницы (`JOB_EPHEMERAL`/память) не позволяют ни
   скачать, ни загрузить модель целиком; «выборочная динамика» не реализована.
6. **Мультитенантность поверхностна**: есть префикс `tenant/<subject>/`, но нет квот, шиейпинга,
   изоляции и per-tenant шифрования; из-за tenant-префикса теряется кросс-тенантная дедупликация.
7. **ИБ/транспорт**: S3 наружу отдан **TCP-passthrough без TLS** (plaintext), длинные presigned-TTL,
   нет mTLS/OIDC, evidence — один писатель.
8. **Эксплуатация/HA**: single replica сервиса, in-memory состояние (`_pending_uploads`, rate-limit),
   хрупкая перепривязка digest, ручные rollout/ConfigMap-дайджесты, нет автоскейла и очередей.

## 1. Ограничения по слоям

### 1.1 Хранилище (S3/Garage)
| # | Ограничение | Влияние на 1 ТБ+ | Что требуется в v3 |
|---|-------------|------------------|--------------------|
| S1 | Один узел, `RF=1`, одна PVC | Потеря узла = потеря данных; нет шардирования | Многоузловой S3-кластер, RF≥2/erasure coding |
| S2 | Ёмкость ограничена (≈сотни ГБ) | Не хватает под ТБ-артефакты и их историю | Горизонтальное расширение, tiering (hot/cold) |
| S3 | Ingest ≈32–43 МБ/с на узел | 1 ТБ ≈ 6–9 ч; ≥10 Гбит/с не используется | Параллельный ingest по узлам, быстрые NVMe/RAID |
| S4 | Нет кво т/лимитов на тенанта | «Шумный сосед» выедает хранилище/сеть | Per-tenant quotas, fair-share, backpressure |
| S5 | Дублирование по тенантам | Один и тот же объект хранится многократно | Дедуп в общем пуле + ссылки тенанта (refcount) |
| S6 | S3 наружу без TLS | Утечка тела/подписи в сети | TLS-listener/passthrough или VPN; mTLS |

### 1.2 Путь данных / ingest
| # | Ограничение | Влияние | Что требуется в v3 |
|---|-------------|---------|--------------------|
| I1 | Legacy-путь двухходовой + двойная запись | Медленнее и дороже; лишний износ диска | Единый direct-to-S3 путь по умолчанию |
| I2 | Мультипарт ограничен ~10000 частей/очередью | На ТБ нужен адаптивный/бóльший part size | Крупные части, шардирование, возобновление |
| I3 | In-memory `_pending_uploads` | Потеря при рестарте/несколько реплик | Полностью персистентные сессии (БД/очередь) |
| I4 | Ingress single-hop, нет приоритетов | Нет классов трафика/приоритета CI | Приоритеты, лимиты, отдельные пулы |
| I5 | Нет сквозного backpressure к клиенту | Штормы загрузок | Квоты/планировщик, 429/Retry-After |

### 1.3 Анализ
| # | Ограничение | Влияние | Что требуется в v3 |
|---|-------------|---------|--------------------|
| A1 | Только префикс 64 МиБ | Не покрывает 1 ТБ; вердикт частичный | Потоковый/инкрементальный обход, sampling+index |
| A2 | Материализация для полной статики | Невозможна на ТБ | Потоковый разбор прямо из S3 (ranges), mmap |
| A3 | Архивы: лимиты 128 МиБ/архив, неглубокий лимит | 1 ТБ архив не пройти | Членный стриминг из S3, индекс, depth учета |
| A4 | Динамика только целиком | ТБ-модели не запускаются | Выборочная динамика на срезах/членах |
| A5 | Частое `Inconclusive` | Меньше доверия к «Safe» | Полнота покрытия, дельта-проверки, отчётность |
| A6 | Нет fuzzing парсеров | Риск 0-day в парсерах | Fuzzing, sandbox-парсеры, SBOM |

### 1.4 Безопасность и изоляция
| # | Ограничение | Влияние | Что требуется в v3 |
|---|-------------|---------|--------------------|
| B1 | S3-passthrough без TLS | Plaintext-трафик | TLS/VPN/mTLS |
| B2 | Длинный presigned-TTL, URL в логах | Компрометация доступа к объекту | Короткий TTL, одноразовость, аудит |
| B3 | Нет mTLS/OIDC | Слабая аутентификация сервисов | mTLS между компонентами, OIDC для людей |
| B4 | Evidence single-writer | Боттлнек/SPOF целостности | Анкоринг во внешнее WORM, репликация |
| B5 | Нет per-tenant KMS | Все тенанты в одном контуре ключей | Per-tenant ключи/E2E-шифрование версий |

### 1.5 Эксплуатация, надёжность, наблюдаемость
| # | Ограничение | Влияние | Что требуется в v3 |
|---|-------------|---------|--------------------|
| O1 | Single replica сервисов | Простой на рестарте | HA, ≥2 реплики, leader-election/locks |
| O2 | Хрупкая перепривязка digest (`SANDBOX_IMAGE` сбрасывается манифестом) | Динамика блокируется Kyverno | Управляемый pinning/SBOM/admission без ручных шагов |
| O3 | ConfigMap-дайджест связывает код/конфиг | Ломает rollout при правке | Версионирование конфигов, подпись |
| O4 | Нет автоскейла/очередей | Деградация под нагрузкой | KEDA/очередь, HPA, планировщик |
| O5 | Метрики из одного источника, нет трейсинга | Сложнее диагностика | Распределённый трейсинг, per-tenant SLO |
| O6 | Ручные runbooks | Человеческие ошибки | Автоматизация, GitOps |

## 2. Сводная таблица «ограничение → требование v3»

| Класс | Ключевое ограничение v2 | Требование v3 |
|-------|-------------------------|---------------|
| Хранилище | Single-node RF=1 | Многоузловой S3, RF≥2/EC, tiering, DR |
| Пропускная | ~40 МБ/с ingest | ≥1 ГБ/с/узел, параллельный ingest, NVMe |
| Путь данных | Двухходовой + материализация | Direct-to-S3 по умолчанию, потоковый анализ |
| Архивы | 128 МиБ/архив, без индекса | Членный стриминг 1 ТБ+, индекс, depth-политика |
| Динамика | Только целые модели | Сэмплированная динамика срезов/членов |
| Мультитенант | Префикс без квот | Квоты, fair-share, изоляция, KMS |
| ИБ | Passthrough без TLS | TLS/mTLS, короткие URL, WORM-анкоринг |
| Эксплуатация | Ручные операции, single replica | HA, очереди/автоскейл, GitOps, трейсинг |

## 3. Вывод

v2 доказала работоспособность концепции и дала инфраструктурную основу (S3, БД, evidence,
пути загрузки). Однако её архитектура **single-node** и **двухходовой/материализующий** путь не
масштабируются на артефакты 1 ТБ+: узкие места в ingest узла, ограничения обхода архивов,
недоступность динамики для ТБ и поверхностная мультитенантность. Отсюда — **v3**
([`../Arch_v3/README.md`](../Arch_v3/README.md)): масштабируемый data-plane, потоковый анализ из S3,
членный обход архивов, сэмплированная динамика, строгая мультитенантность и безопасный транспорт.
