# 03. Data-plane v3: распределённое S3-хранилище

## 1. Цели

- Хранить **≥ 1 ТБ** на объект и петабайтные объёмы в целом.
- Горизонтально масштабироваться по ёмкости и пропускной способности.
- Обеспечить **долговечность** (RF≥2/erasure coding) и **доступность** (≥3 узла).
- Дедуп по содержимому в **общем пуле** с изоляцией тенантов.
- Разделить «горячий» (NVMe) и «холодный» (HDD/S3) tiers.

## 2. Топология

- **Storage nodes** (≥3): отдельный node pool с NVMe (hot) и HDD (cold); S3-совместимый сервис
  (Garage multi-node / MinIO distributed / Ceph RGW — выбор при реализации, `15-implementation-plan.md`).
- **Шардинг**: объект разбивается на chunks; chunks распределяются по узлам (hash/ring).
- **Репликация**: `RF=2..3` или **erasure coding** (k+m) для больших объектов; политика на уровне bucket.
- **Metadata**: распределённый/реплицируемый индекс (у самих S3-узлов) + PostgreSQL для прикладных
  метаданных (реестр, сканы).
- **Tiering**: lifecycle-правила переносят «холодные» объекты на cold tier; метаданные остаются
  горячими (быстрый листинг/поиск).

## 3. Пространство ключей и дедупликация

- **Общий пул**: ключ `objects/<sha256[0:2]>/<sha256[2:4]>/<sha256>` (без тенанта) → глобальный дедуп.
- **Тенант-ссылки**: таблица `object_refs(tenant_id, sha256, name, first_seen, refcount, bytes)`.
  Один физический объект используется несколькими тенантами; удаление — по `refcount=0` (GC).
- **Изоляция**: ACL на уровне API (тенант видит только свои ссылки); физический объект — в общем пуле.
- **Опционально per-tenant KMS**: envelope-шифрование «ключом тенанта» при записи (дедуп в этом
  случае работает только внутри тенанта; политика выбирается на уровне tenant tier).

**Эффект**: дедуп между тенантами (запрещён в v2 из-за tenant-префикса) — экономия ≥30 % на
повторных загрузках (требование N11).

## 4. Поток чтения для анализа

```
Analysis worker ──range GET (offset,len)──▶ S3 (любой узел) ──▶ chunk shards
```
- **Range-read**: анализ запрашивает только нужные диапазоны (заголовок, индекс, сэмплы).
- **Node-local NVMe cache**: read-through кэш «горячих» диапазонов на compute-узле; CoW + TTL;
  повторные проверки/члены читаются локально.
- **Parallel fetch**: index-driven обход параллелит диапазоны (16–64 потока) с backpressure.
- **Нет материализации** объекта целиком (кроме объектов в пределах лимита песочницы).

## 5. Долговечность, DR, retention

- **RF/EC** + scrubing (периодическая проверка целостности chunks); обнаружение и восстановление.
- **DR**: multi-site репликация (async) или backup в другой S3; цели RPO ≤ 15 мин, RTO ≤ 1 ч (N7).
- **Retention/lifecycle**: TTL артефактов/карантина; tombstone-записи; WORM-копии evidence.
- **Интегритет**: checksum (sha256) при приёме и периодическая верификация; несовпадение → алёрт.

## 6. API data-plane (внутренний)

| Операция | Назначение |
|----------|------------|
| `presign_part(key, upload_id, part, ttl)` | presigned-URL части (короткий TTL) |
| `range_get(key, off, len)` | чтение диапазона (потоково) |
| `object_stat(key)` | размер/etag/checksum (манифест) |
| `ref_add/ref_del(tenant, sha256)` | ссылки тенанта (refcount) |

## 7. Масштабирование и capacity

- **Пропускная**: ≥1 ГБ/с/узел (NVMe), агрегат ≥5 ГБ/с (N1); параллельный ingest/чтение.
- **Ёмкость**: линейно по узлам; cold tier для архивов/истории.
- **Backpressure**: при насыщении — 429/`Retry-After`, приоритеты для CI.
- **Рост**: добавлять storage-узлы без простоя (перебалансировка chunks).

## 8. Что переиспользуется из v2

- Клиент `s3client.py` (SigV4, multipart, presign, `list_parts`, retry) — расширяется range-get,
  большими частями, работой с распределённым кластером.
- content-addressed модель и дедуп — сохраняются, но ключ уходит от `tenant/…` к общему пулу + refs.
