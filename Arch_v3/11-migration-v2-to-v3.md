# 11. Миграция v2 → v3

Цель — перейти на v3 **без простоя** и без потери данных/evidence, поэтапно, с возможностью отката.

## 1. Принципы

1. **Параллельная работа**: v2 и v3 (новые компоненты) сосуществуют до переключения.
2. **Совместимость API**: клиентский протокол загрузки/скана расширяется, старые вызовы поддерживаются.
3. **Данные не удаляются** до успешной верификации в v3.
4. **Evidence непрерывна**: цепочка v2 переносится/анкорится, целостность проверяется.
5. **Обратимость**: каждый шаг имеет rollback.

## 2. Этапы миграции

| Этап | Что делаем | Проверка | Откат |
|------|-----------|----------|-------|
| M0 | Развернуть v3-стек (storage pool, control, analysis) **рядом** с v2 | health/smoke | удалить новые ns |
| M1 | Ввести общий пул объектов + refs; настроить dual-write реестра | cross-check v2↔v3 метаданных | выключить dual-write |
| M2 | Перевести ingest на v3 (presigned через TLS edge) для новых загрузок | e2e с АРМ, 1 ТБ harness | вернуть v2 ingress |
| M3 | Включить потоковый анализ v3 (static/archive) на новых сканах | e2e/perf/coverage | вернуть v2 анализ |
| M4 | Перенести/анкорить evidence; верифицировать HMAC-цепочку | verify + WORM-анкор | оставить v2 evidence read-only |
| M5 | Переключить UI/API/gate на v3; v2 — read-only | UI/e2e/SLO | вернуть v2 UI |
| M6 | Вывести v2 из эксплуатации (после стабилизации) | 2 недели SLO | восстановить v2 из бэкапов |

## 3. Миграция данных

- **Объекты S3**: v2-ключи `sha256/…` и `tenant/<t>/<sha>/…` → v3-ключ `objects/<sha…>`.
  Копирование server-side (в пределах хранилища) + построение `object_refs`; дедуп схлопывает
  одинаковые объекты; исходные объекты сохраняются до верификации.
- **Метаданные**: таблицы `artifacts/scans/findings/uploads` → расширяются
  (`object_refs`, `upload_sessions` персистентность, `members` для архивов).
- **Evidence**: `evidence.jsonl` + БД переносятся; цепочка HMAC проверяется; голова анкорится в WORM.
- **Политики/ключи**: `policy.json`, API-ключи, tenant-настройки/квоты переносятся.

## 4. Совместимость API

| v2 | v3 | Совместимость |
|----|----|---------------|
| `POST /scans/upload` | сохраняется (deprecated) | работает, но рекомендован direct |
| `POST /uploads/initiate` | расширяется (TLS, квоты) | ответ дополняется полями |
| `GET /uploads/<id>/parts` | сохраняется | + свежие URL, TTL |
| `POST /scans/complete` | сохраняется | + refcount/manifest |
| `GET /scans/<id>` | расширяется (`coverage`, члены) | новые поля опциональны |

## 5. Риски и их митигация

| Риск | Митигация |
|------|-----------|
| Расхождение метаданных | dual-write + сверка + reconcile-job |
| Потеря/порча объектов | копирование server-side + контрольные суммы + проверка |
| Разрыв evidence | карантин, ручная верификация, анкор до переключения |
| Деградация под нагрузкой | поэтапное переключение тенантов, canary |
| Откат | сохранение v2-стеклинга до стабилизации |

## 6. Критерии готовности миграции

- e2e (в т.ч. с АРМ) зелёные на v3.
- 1 ТБ model + 1 ТБ archive harness пройдены (см. `12-testing-strategy.md`).
- Evidence verify = ok; WORM-анкор выполнен.
- SLO (N1–N7) выполняются ≥ 2 недели.
- Данные v2 верифицированы в v3; v2 можно выводить.
