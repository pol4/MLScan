# 09. Наблюдаемость, SLO и capacity v3

## 1. Цели

- Давать **сквозную картину** по фазам (ingest → хранение → анализ → вердикт → evidence).
- Обеспечить **per-tenant SLO** и fair-share.
- Обеспечить **capacity planning** под 1 ТБ+ и петабайтные объёмы.
- Оповещать о деградации/нарушениях целостности.

## 2. Метрики по слоям

| Слой | Метрики |
|------|---------|
| Ingest | байты/с, МБ/с по фазам (приём/части/complete), активные загрузки, 429/retry, TTL-resume |
| Data-plane | занято/свободно по узлам, ingest/egress ГБ/с на узел и агрегат, refcount/дедуп %, scrub-ошибки |
| Static | прочитано байт/диапазонов, время до первого результата, полное время, покрытие % |
| Archive | число членов, обработано/пропущено, depth-срабатывания, бюджет-остановы |
| Dynamic | Job success rate, время, maxrss, покрытие динамики, honeypot/sinkhole-события |
| Вердикт | распределение по вердиктам, `inconclusive_ratio`, findings/скан, coverage-порог |
| Evidence | entries, signed, chain-verify ok, WORM-анкоринг возраст |
| Тенанты | квоты (использовано/лимит), приоритет, SLO по тенанту |
| Платформа | CPU/RAM/диск узлов, сетевые ошибки, HA/leader-состояние |

## 3. SLO (из `01-requirements.md`)

- N1/N2 — пропускная ingest/утилизация канала.
- N3/N4/N5 — время анализа (первый результат, статика, архивы).
- N6 — доступность 99.9 %.
- N7 — RPO/RTO.
- N8/N9 — FP и покрытие.

## 4. Трейсинг и корреляция

- Распределённый трейсинг (OpenTelemetry): трейс скана от `initiate` до `evidence`.
- Корреляционные ID: `tenant`, `scan_id`, `sha256`, `upload_id`, `job_id`.
- Логи — структурные (JSON), с уровнями и trace-id.

## 5. Алёрты (примеры)

| Алёрт | Условие | Действие |
|-------|---------|----------|
| `ingest_below_floor` | ingest < 50 % от N1 | масштабировать/диагностировать узлы |
| `scrub_error` | несовпадение chunk | восстановить из реплик/EC |
| `evidence_broken` | провал verify-цепочки | стоп приёма решений, расследование |
| `coverage_low` | доля `Inconclusive` растёт | проверить детекторы/бюджеты |
| `quota_exhausted` | тенант у лимита | throttle/уведомление |
| `queue_backlog` | очередь сканов растёт | автоскейл воркеров |
| `dynamic_fail_rate` | рост провалов Job | проверить песочницу/образы |

## 6. Capacity planning

- Модель: **объём** (сырые данные × (1+overhead) − дедуп) + **метаданные** + **история сканов**.
- Пропускная: пики ingest/чтения; cold tier для «холодных» архивов.
- Оценка для 1 ТБ: время ingest ≈ 1 ТБ / агрегат-ГБ/с; анализ ≈ индекс + сэмплы.
- План роста: добавление storage-узлов, расширение cold tier, автоскейл analysis-воркеров.

## 7. Дашборды

- **Data-path**: ingest/чтение по фазам и узлам, утилизация канала.
- **Analysis**: очереди, времена, покрытие, вердикты.
- **Tenants**: квоты, SLO, приоритеты.
- **Health**: HA/leader, evidence, scrub, DR-статус.

## 8. Отличия от v2

v2 давал базовые `mlscan_*`/`mlscan_upload_*` и `/quality` без per-tenant SLO, трейсинга и capacity
модели. v3 добавляет per-tenant наблюдаемость, трейсинг и планирование ёмкости под ТБ+.
