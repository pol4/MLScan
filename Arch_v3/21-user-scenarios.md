# 21. Типовые пользовательские сценарии MLScan (на согласование перед переделкой UI)

Документ описывает **целевые** пользовательские сценарии и целевую структуру интерфейса. Переделка UI
выполняется только после согласования этого документа. Раздел §8 содержит открытые вопросы — по ним нужно
решение.

## 1. Термины

| Термин | Значение |
|---|---|
| **Артефакт** | загруженный объект: модель (safetensors/ONNX/HDF5/Keras/pickle/GGUF), архив, датасет |
| **Инференс** | запускаемый движок (образ по digest), который может исполнять модель: `llama.cpp` (GGUF/LLM), vLLM/ONNX-Runtime и т.п. Регистрируется вручную (импорт по digest) |
| **Связка (bundle)** | неизменяемая комбинация «артефакт + инференс + версии правил/набора вопросов»; фиксируется для повторяемости |
| **Скан** | проверка артефакта (статика + динамика в песочнице); результат — вердикт и находки |
| **Тест (инференс-прогон)** | прогон модели на движке по набору вопросов с наблюдением поведения (in-guest eBPF); результат — вердикт инференса и аттестация |
| **Набор тестов** | XLSX с вопросами/критериями (активный набор задаёт, что спрашивать у модели) |

## 2.0 Концепция: **движок есть у любого артефакта**

Каждая проверка в системе — это исполнение артефакта **движком** (engine), и результат фиксируется как
неизменяемая связка «артефакт + движок + версии» (bundle):

| Артефакт | Движок | Выбор движка |
|---|---|---|
| pickle / скрипты / «инертные» форматы (safetensors, ONNX, HDF5, Keras, архивы, тексты) | **песочный движок платформы** (Kata + harness, проверка загрузки и поведения) | дефолт, выбирать не нужно |
| датасет (с HF) | **песочный движок платформы** + правила датасетов | дефолт |
| LLM (GGUF и др.) | **внешний инференс-движок** (например `llama.cpp:server-cuda` по digest) | **обязательный выбор, без дефолта** |

Песочный движок регистрируется в реестре как обычный движок (ссылка по digest на образ песочницы,
`source=builtin`) — тогда «связывание» и bundle единообразны для всех типов артефактов, а в истории видно,
каким движком проверялся артефакт.

## 2. Целевая структура интерфейса

| Раздел | Содержимое |
|---|---|
| **Настройки** | только личное: **HF-токен пользователя**, **набор тестов (XLSX)**, язык |
| **Администрирование** | квоты HF, rate-limit, журналы (решения gate, egress), целостность цепочки вердиктов, движки/подписи, версия платформы |
| **Сканы** | **единый список артефактов** (модели/архивы/датасеты): статус, вердикт, дата, связанный инференс. Клик по строке → **история тестов артефакта** (все прогоны, вердикты, аттестации). Кнопки: **связать/сменить инференс**, **запустить тест**, **повторить тест** |
| **Загрузка локальных артефактов** | подзакладки: **Модели** (файлы/архивы) и **Инференсы** (движки: импорт по digest, подпись, SBOM) |
| **Загрузка с HF** | переключатель **Модели / Датасеты**, обзор доступного (как на сайте HF: первая страница результатов), фильтры (автор/организация, назначение/pipeline), очередь на скачивание и статусы |
| **История операций** | по каждой подзакладке — журнал операций (что загружали, когда, результат/ошибка) |

Что меняется относительно текущего UI (по вашим пунктам 1–7):

1. «Набор тестов (XLSX)» переносится из раздела «Загрузки» в **Настройки**.
2. HF-токен вводится и сохраняется **в Настройках**, привязан к учётной записи залогинившегося пользователя.
3. Блок HF-токена удаляется из «Загрузка с HF» (там только поиск/обзор).
4. Отдельная подзакладка **«Сканы»** — список сканов и их результатов; в остальных подзакладках списка
   сканов нет, вместо него — **истории операций** этих подзакладок.
5. Состав подзакладок: **Сканы**, **Загрузка локальных артефактов** (модели и инференсы),
   **Загрузка с HF** (модели и датасеты).
6. «Загрузка с HF» — режим **просмотра доступного** (первая страница выдачи моделей/датасетов),
   переключатель «Модели/Датасеты», фильтры (разработчик, назначение), затем выбор и **постановка в очередь**.
7. Базовый сценарий: загрузка модели и/или инференса → **связывание** → запуск теста → **подробный**
   просмотр результата; возможность **изменить связь** и **повторить тест**, пока артефакт доступен.

## 3. Базовый сквозной сценарий (главный)

1. Вход.
2. **Настройки**: сохранить личный **HF-токен** (если нужны приватные/лимитированные модели), загрузить
   **набор тестов XLSX** (он становится активным).
3. **Загрузка локальных артефактов → Инференсы**: зарегистрировать нужные движки (импорт по digest;
   при необходимости — подписать, приложить SBOM).
4. **Загрузка локальных артефактов → Модели** (или **Загрузка с HF**): загрузить модель/архив/датасет.
5. **Сканы**: в списке появляется артефакт. Для моделей, требующих инференса (LLM, поведенческий анализ),
   — **указать инференс** из зарегистрированных (по умолчанию подставляется подходящий, см. §8-вопрос 4).
6. **Запустить тест** из строки артефакта (или из истории артефакта).
7. **Просмотреть результат**: вердикт, покрытие, **детализация находок** (см. §5), для LLM — ответы
   модели по вопросам и почему они признаны опасными, аттестация.
8. При необходимости — **сменить инференс** и **повторить тест** (артефакт ещё в хранилище).

## 4. Сценарии по ролям

### U1. Первичная настройка (аналитик)
Настройки → HF-токен → набор тестов XLSX → проверить активный набор; язык интерфейса.

### U2. Локальная модель (не-LLM): загрузка → тест → результат
Модели → файл/архив → «Сканы» → (инференс не требуется) → «Запустить тест» → результат с детализацией по
каждому правилу. Для архивов — результат по каждому элементу (включая вложенные).

### U3. Локальная LLM: загрузка → связывание с инференсом → тест → результат
Модели (GGUF) → выбрать **инференс** (например `llama.cpp:server-cuda` по digest) → «Сканы» → «Запустить
тест» → вердикт инференса, ответы по вопросам, поведенческие находки `LLM-B-*`.

### U4. Загрузка инференса (движка)
Загрузка локальных артефактов → Инференсы → `ref@sha256:…` → Импорт → (подпись/SBOM) → движок доступен
для связывания. Если включено требование подписи — без подписи связать тест нельзя (понятная ошибка).

### U5. Модель с HF: обзор → фильтры → очередь → тест
Загрузка с HF → переключатель **Модели** → фильтры (организация, назначение) → страница выдачи (как на
сайте) → «В очередь» → по завершении артефакт в «Сканах» → связывание с инференсом → тест.

### U6. Датасет с HF
Загрузка с HF → переключатель **Датасеты** → фильтры → очередь → по завершении артефакт типа `dataset`
в «Сканах» → «Запустить тест» (проверка содержимого на опасные файлы/скрипты; инференс не требуется).

### U7. Повторный тест и смена связи
«Сканы» → строка артефакта → история тестов → «Сменить инференс» → «Повторить тест». В истории видны все
предыдущие прогоны, вердикты, аттестации (и звенья цепочки вердиктов).

### U8. Проверка в CI (админ/инженер)
Выдать короткоживущий JWT → вызов `GET /gate?image=…&model=…` → решение (`allow|block|quarantine`) и
аттестация.

### U9. Администрирование
Настройки (админ): квоты HF-загрузок, rate-limit, журнал решений gate, журнал egress HF, проверка
целостности цепочки вердиктов (`/v3/evidence/verify`), состояние сенсора (`/v3/slo.sensor_coverage`).

## 5. Требуемая детализация результатов (важно)

Сейчас результат слишком «высокоуровневый» (например, «Запуск shell/интерпретатора»). Нужно показывать по
каждой находке:

| Поле | Смысл |
|---|---|
| Правило | `LLM-B-01`, `PKL-03`, `FMT-00`… |
| Серьёзность / уверенность | high/critical, 0.8 |
| Фаза и проба | `load` / `probe`, номер вопроса (для LLM) |
| **Вопрос и ответ модели** | текст вопроса и полный ответ модели (для LLM/поведенческого анализа) |
| **Почему признано опасным** | сработавшее правило/критерий и улика (фрагмент ответа, путь файла, IP, аргументы вызова) |
| Для pickle/скриптов | цепочка вызовов (что именно вызвано: `os.system`, `subprocess`, сеть, файлы) |
| Для архивов | путь элемента внутри архива (+ вложенность) |
| Аттестация | `attestation_digest`, подпись, версии (набор тестов, движок, детекторы) |
| Экспорт | кнопка/эндпоинт выгрузки отчёта (JSON; при необходимости — PDF) |

## 6. Что остаётся неизменным

Логика безопасности и API: песочница Kata, in-guest eBPF-сенсор (`LLM-B-01…05`), аттестация и подпись
вердиктов, неизменяемая цепочка вердиктов, журналы gate/egress, квоты/лимиты, CI-gate. Меняется
**компоновка UI** и **детализация отчётов**, а не модель безопасности.

## 7. Полный браузерный тест со скриншотами (после переделки)

Скрипт `tests/ui/full_browser_e2e.js` будет расширен: на каждом шаге — **скриншот** (PNG) в
`docs/img/ui-e2e/NN-step.png` + журнал шагов; сценарий: U1 (настройки) → U4 (инференс) → U2 (локальная
модель) → U3 (локальная LLM + тест) → U5 (модель с HF + тест) → U6 (датасет) → U7 (повторный тест/смена
инференса) → проверка детализации результата. Итог: набор скриншотов + отчёт-документ снимка экрана по
каждому шагу.

## 8. Согласованные решения

| Вопрос | Решение |
|---|---|
| Дефолт для простых форматов | **Песочный движок платформы** (оформляем существующий код запуска pickle/скриптов как отдельный «движок» и используем его по умолчанию). Для **LLM** — **обязательный выбор движка**, без дефолта |
| Датасеты с HF | **Проверка содержимого + отдельные правила для датасетов** (подозрительные скрипты, data-яды, несоответствие формата), без инференса |
| Админ-функции | **Выносятся из «Настроек»** в отдельный раздел **«Администрирование»** |
| Скриншоты теста | **PNG** на каждый шаг (`docs/img/ui-e2e/`) **+ отдельный раздел с ключевыми снимками в инструкции** |
| Экспорт результатов | **JSON-отчёт + печатная форма** (HTML для печати в PDF браузером) |

Также согласовано: концепция «**под любую модель или данные в системе есть движок**» вносится в
концептуальные документы (`Arch_v3/02-architecture.md`) и на **первую страницу** (README).
