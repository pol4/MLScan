# 20. Инструкция по работе с системой MLScan (проверка моделей ML/AI)

Документ описывает **фактический** порядок работы с развёрнутой системой (интерфейс, API, результаты).
Все шаги проверены сквозным браузерным прогоном `tests/ui/full_browser_e2e.js` (16 шагов, реальные
модели: локальный GGUF 278 МБ, модель с Hugging Face 291.5 МБ, safetensors, архив) — см. §9.

## 1. Что можно проверять

| Тип | Как подавать | Что делает система |
|---|---|---|
| Не-LLM модель (safetensors, ONNX, HDF5, Keras, pickle, GGUF как артефакт) | «Загрузки → Модели» | статический разбор + динамический прогон в песочнице Kata (безопасные загрузчики), вердикт и покрытие |
| Архив (zip/tar) с моделями | «Загрузки → Модели» | обход архива с ограничением глубины, проверка каждого файла, вердикт по худшему |
| LLM (GGUF) — локальный файл | «Загрузки → Локальные LLM» (обязателен движок) | загрузка, скан, **bundle** (движок+модель) и запуск **теста инференса** |
| LLM с Hugging Face | «Загрузки → Модель с HF» | реальный поиск/скачивание, bundle, затем тест инференса |
| Образы движков | «Загрузки → Движки» | регистрация образа по digest, подпись и SBOM |

Ограничения и лимиты: размер одного файла до `HF_MAX_FILE_BYTES` (8 ГиБ), суточная квота скачивания с HF
на тенанта (`HF_DAILY_BYTES`, по умолчанию 200 ГиБ), частота запросов к API ограничена (429 при
превышении). Детали — §8.

## 2. Быстрый старт (5 шагов)

1. Откройте интерфейс, войдите под своей учётной записью.
2. Прокрутите к разделу **«Загрузки»** и выберите подзакладку по типу данных (§3).
3. Загрузите файл (для LLM обязательно выберите **движок** из списка «engine: …»; для HF — введите
   поисковый запрос и при необходимости HF-токен).
4. Дождитесь завершения обработки: появится запись в таблице артефактов и/или строка статуса.
5. Откройте карточку артефакта (ссылка в строке) — вердикт, покрытие, находки. Для LLM запустите
   **«Тест bundle»** (подзакладка «Тест bundle»), чтобы выполнить инференс и получить вердикт bundle.

## 3. Раздел «Загрузки»: четыре подзакладки

| Подзакладка | Назначение | Ключевые элементы |
|---|---|---|
| **Модели** | загрузка обычных файлов и архивов | поле выбора файла, тип (auto/…), кнопка «Загрузить» |
| **Локальные LLM** | загрузка GGUF-модели и создание bundle | выбор файла, список «engine: …», кнопка «Загрузить», строка статуса (созданный `bundle b-…`) |
| **Движки** | регистрация образов движков, подпись, SBOM | поле `ref@sha256:…`, кнопки «Импорт» и «Подписать», список зарегистрированных движков с пометками `[signed]/[unsigned]/[sbom]` |
| **Модель с HF** | поиск и скачивание с Hugging Face | поле запроса, фильтр типа, квантизация, выбор движка, кнопка «Найти», результаты с кнопками скачивания, строка статуса (прогресс, sha, bundle) |
| **Тест bundle** | инференс на наборе вопросов | поля `sha256 модели` (или `bundle_id`), кнопка «Прогнать тест», статус: `тест запущен: job …, вопросов N, GPU/CPU` → `тест завершён: вердикт …, решение …, аттестация …` |

HF-токен (для приватных репозиториев): поле «токен» и кнопка «Сохранить» — значение маскируется
(`saved hf_***1234`), хранится зашифрованным на тенанта; пустое значение удаляет токен.

## 4. Сценарии пошагово

### S1. Не-LLM модель (safetensors/ONNX/…)

1. «Загрузки → Модели» → выбрать файл → «Загрузить».
2. Дождаться появления строки в таблице артефактов.
3. Открыть карточку артефакта: **вердикт** (`Safe` / `Inconclusive` / `Dangerous` / …), **покрытие**
   (статика/динамика), список находок с правилами (`PKL-*`, `FMT-*`, `A-*` и т.д.).
4. Для архивов в карточке перечислены проверенные элементы (включая вложенные архивы).

Пример из прогона: реальный `safetensors` (64 КБ) → `Inconclusive` (статическая часть пройдена,
динамика по формату неполная — это штатное поведение «нет полного покрытия»);
реальный `zip` (119 КБ, внутри safetensors + pickle + вложенный zip) → `Dangerous`.

### S2. Локальная LLM: загрузка → скан → **инференс**

1. «Загрузки → Локальные LLM»: выбрать движок (например, `engine: …llama.cpp@sha256:…`), выбрать
   GGUF-файл, «Загрузить». В статусе появится `bundle b-… (тест запущен)`.
2. «Загрузки → Тест bundle» → вставить **sha256 модели** (или `bundle_id`) → «Прогнать тест».
3. Система создаст job (движок + набор вопросов), выполнит инференс и вернёт в строке статуса:
   `тест завершён: вердикт …, решение …, аттестация sha256:…`.
4. Тот же результат доступен в API: `POST/GET /bundles/<id>/test`, `GET /bundles/<id>/verdict`.

Пример из прогона: реальный GGUF `gemma-3-270m-it-Q8_0.gguf` (278 МБ) → bundle → инференс →
`вердикт Needs review, решение block, аттестация sha256:9a416ec2…`.

### S3. Модель с Hugging Face → **инференс**

1. (для приватных репо) сохранить HF-токен.
2. «Загрузки → Модель с HF»: запрос (например `gemma-3-270m-it-GGUF`), тип `text-generation`,
   квантизация `Q8_0`, выбрать движок → «Найти».
3. В результатах нажать скачивание у нужного репозитория; статус покажет прогресс и по завершении —
   `download <id>: done <байт>/<байт>`, sha модели и созданный bundle.
4. «Загрузки → Тест bundle» → sha модели → «Прогнать тест» → вердикт и аттестация.

Пример из прогона: поиск вернул 14 репозиториев; `unsloth/gemma-3-270m-it-GGUF` (Q8_0) скачана за **40 с
(291.5 МБ)**; инференс → `вердикт Needs review, решение block, аттестация sha256:35505d7c…`.
Во время инференса in-guest eBPF-сенсор зафиксировал находки `LLM-B-01`, `LLM-B-03`, `LLM-B-04`.

### S4. Архив моделей

Как S1, но подаётся `zip`/`tar`. Система обходит архив (с ограничением глубины) и возвращает вердикт по
худшему элементу; поддержаны все форматы, которые понимают загрузчики.

### S5. Движок не подошёл: перепривязка и повторный тест

Панель «Перепривязка»: указать sha256 модели, выбрать другой зарегистрированный движок → «Перепривязать».
Создаётся новый bundle (движок+модель+версии); далее — снова «Тест bundle».

### S6. Автоматическая проверка в CI (gate)

```
GET /gate?image=<ref@sha256:…>&model=<sha256 модели>
→ {"decision":"allow|block|quarantine","source":"bundle-verdict|bundle-no-verdict|artifact-verdict|policy-default",
   "verdict":"…","attestation_digest":"sha256:…","signature":"…"}
```

`block` — вердикт с критичными отказами; `quarantine` — нет вердикта/неполное покрытие (fail-closed);
`allow` — только при положительном вердикте. Для CI удобно выдать короткоживущий JWT (§8).

### S7. Повторный тест после обновления правил/набора вопросов

Загрузите обновлённый XLSX в «Загрузки» (набор вопросов) и повторите «Тест bundle» — вердикт и
аттестация пересчитываются, в цепочку вердиктов добавляется новое звено.

## 5. Вердикты модели и решения gate

| Вердикт артефакта | Смысл |
|---|---|
| `Safe` | находок нет, покрытие полное |
| `Inconclusive` | проверка неполная (формат/динамика не покрыты) — требуется ручное решение |
| `Dangerous` / `Malicious` | найдены опасные признаки (загрузка кода, pickle-вызовы, эксплойт-паттерны…) |
| `Needs review` | требуется ручная проверка (например, неполные ответы модели) |

Вердикт bundle (после инференса): `Safe` — все вопросы пройдены; `Needs review` — есть критичные отказы
(`safety_fail > 0`); `Inconclusive` — частичный результат. Каждый вердикт bundle подписывается
(аттестация `sha256:…`) и добавляется в неизменяемую цепочку (§7).

## 6. Движки: регистрация, подпись, SBOM

1. «Загрузки → Движки»: указать `ref@sha256:…` → «Импорт» (движок становится доступен во всех списках).
2. «Подписать» — платформенная подпись digest (interim к cosign); в списке появится `[signed]`.
3. При включённой политике `IMAGES_REQUIRE_SIGNED=1` создание bundle/перепривязка/HF-загрузка требуют
   **подписанный** движок (иначе 400 с пояснением). SBOM образа хранится рядом с подписью
   (`POST /images/<digest>/sbom`).

## 7. Аудит, наблюдаемость, целостность

| Что | Как получить |
|---|---|
| Журнал решений gate (append-only) | `GET /gate/decisions?model=<sha>&limit=N` |
| Журнал egress HF (append-only) | `GET /hf/egress?limit=N` |
| Проверка целостности вердиктов | `GET /v3/evidence/verify` → `{"ok":true,"count":N,"head":"…"}` |
| Метрики | `GET /v3/metrics` (в т.ч. `mlscan_hf_*`, фазы пайплайна) |
| SLO/алерты | `GET /v3/slo` (в т.ч. `sensor_coverage` — доля LLM-тестов, где сенсор прислал события) |

Пример из прогона: цепочка вердиктов `ok=true`, звеньев 7 (звено добавляется при каждом вердикте bundle).

## 8. Квоты, лимиты, токены для CI

* Суточная квота HF на тенанта: `GET/POST /hf/quota` (admin; `daily_bytes: null` — снять персональный
  лимит). При превышении загрузка завершается ошибкой, в журнал пишется `denied`.
* Ограничение частоты: 429 + `Retry-After`; настраивается `GET/POST /rate-limit` (admin; `rps=0` —
  выключить). Загрузки частями и `/healthz` под лимит не попадают.
* Токен для CI: `POST /auth/token` (admin) → короткоживущий JWT (`subject`, `roles`, `ttl`), далее
  `Authorization: Bearer <token>` (проверяются подпись HS256, `exp`, `aud`, `iss`).

## 10. Диагностика

| Симптом | Причина и действие |
|---|---|
| `ERR: выберите движок из уже скачанных` | в «Движки» не зарегистрирован образ по digest — импортируйте его |
| `модель bundle не найдена в хранилище` | модель не загружена в систему: загрузите файл (S1/S2) или скачайте с HF (S3) |
| Тест bundle: `движок bundle не найден в registry_images` | движок удалён/не зарегистрирован — импортируйте заново |
| Вердикт `Inconclusive` | неполное покрытие (формат/динамика) — нормально для части форматов; смотрите покрытие в карточке |
| Долгий «Тест bundle» | ожидание GPU-слота; для мелких моделей укажите CPU-движок (`runtime_class=kata`, `gpu=false` через API) |
| `429` при частых запросах | сработал rate-limit: подождите `Retry-After` либо поднимите лимит (`POST /rate-limit`) |
| `401` при вызове API | неверный/просроченный ключ или JWT; для /llm/* внутри кластера используется одноразовый run-token |
| HF-поиск/скачивание не работает | проверьте egress-политику HF (`mlscan-hf-egress`) и квоту (`/hf/quota`); адреса HF ротируются — перегенерировать `deploy/ingress/gen-hf-egress.sh` |

## 11. Что смотреть в отчёте по LLM (инференс)

* **Вердикт bundle** и **аттестация** (`attestation_digest`, подпись) — карточка вердикта.
* **Находки поведения** `LLM-B-*` из in-guest eBPF: `B-01` запуск shell/интерпретатора, `B-02` внешний
  egress (только публичные адреса), `B-03` чтение honeypot-секретов, `B-04` исполняемая память (RWX/JIT),
  `B-05` загрузка модуля ядра (`critical`).
* **События сенсора** (`sensor_events`) и `sensor_coverage` в `/v3/slo` — подтверждение, что наблюдение
  работало во время прогона.
