# 20. Инструкция оператору проверки моделей (MLScan v3)

Документ для оператора/аналитика, который **загружает модели и интерпретирует результаты**.
Он не требует знания внутренностей: все действия — через веб-интерфейс или API, а выводы — по
явным правилам ниже. Технические детали: `02-architecture.md`, `15-implementation-plan.md`,
`19-implementation-as-built.md`.

## 0. Роли, доступы, адреса

| Что | Значение |
|-----|----------|
| UI (веб-интерфейс) | `http://analytics.mlscan.local:30217` (HTTPS: `https://analytics.mlscan.local:30921`) |
| API (сервис тестирования) | `http://api.mlscan.local:30217` (или NodePort/port-forward вашего стенда) |
| Логины UI | выдаёт администратор (`admin`, `analyst`); смена — через администратора |
| API-ключи | выдаёт администратор; роли: `admin`, `ci-reader` (для CI), `service`. Ключ передаётся как `Authorization: Bearer <KEY>` |
| Образы инференса | реестр `mlscan-registry`; запуск — **только по digest** |
| S3/артефакты | Garage (внутреннее); наружу — по presigned/TLS-адресу, выданному системой |

> Оператору **не нужны** секреты кластера. Ключи не публикуйте и не вставляйте в имена файлов.

## 1. Требования к передаче данных

### 1.1 Что можно проверять

| Вид артефакта | Как загружать | Обязательные данные |
|---------------|---------------|---------------------|
| Модель (не-LLM): sklearn/torch/ONNX/HDF5/… | UI → «Загрузки → Модели (кроме LLM)», либо API `/scans/upload` | имя файла, формат (`fmt`) |
| LLM (GGUF/квантизация) из файла | «Загрузки → Локальные LLM» (файл + **обязательный выбор движка**) | файл, движок из уже скачанных |
| LLM с **Hugging Face** | «Загрузки → Модель с HF» (поиск + фильтры) | **HF-токен** (если репозиторий закрытый), **выбор движка** |
| Архив моделей (все форматы, вложенные) | «Модели (кроме LLM)»: `fmt=zip`/`tar` | сам архив |
| Движок инференса | «Загрузки → Движки инференса» (импорт по digest) | ссылка `…@sha256:…` или OCI-архив в S3 |
| Датасет/документ/скрипт/ноутбук | «Модели (кроме LLM)» (соответствующий `fmt`) | файл |

Форматы и что по ним проверяется — см. `13-formats.md`; перечень доменов/критериев для LLM —
`16-llm-inference-testing.md` §5.

### 1.2 Передача небольших и больших файлов

- **Из UI**: кнопка загрузки с индикатором прогресса; для LLM обязателен выбранный движок.
- **Через API** (удобно для больших файлов и CI):
  ```bash
  # прямой потоковый POST (шаг чтения 1 МиБ, SHA-256 считается на лету)
  curl --noproxy '*' -X POST -H "Authorization: Bearer $KEY" \
       --upload-file ./model.bin \
       "http://api.mlscan.local:30217/scans/upload?name=model.bin&fmt=safetensors"
  ```
  Ответ `202` содержит `scan_id`, `size`, `sha256`, `s3_key`, `multipart`, `parts`.
- **Очень большие файлы (ТБ-класс)**: используйте **прямую загрузку в S3**
  (`/uploads/initiate` → части напрямую в S3 → `/scans/complete`) — см. §5 приложения.
  Требуется предварительно вычислить `sha256` и `size`.
- **Дедупликация**: объект адресуется по `sha256`; повторная загрузка того же содержимого не
  перезаписывается (`dedup`), проверка переиспользуется.

### 1.3 Лимиты и правила (что нужно учесть заранее)

| Параметр | Значение (по умолчанию) | Что делать |
|----------|--------------------------|-----------|
| Макс. размер загрузки | **1 ТиБ** (`MAX_UPLOAD`) | больше — согласовать с админом |
| Статика (подпись/опкоды/индекс) | первые **64 МиБ** | индексные форматы (safetensors/GGUF/ONNX) читаются целиком по индексу |
| Чтение членов архива | **32 МиБ/член, 128 МиБ/архив**, лимит числа членов | большие архивы проверяются выборочно, с бюджетами |
| Частота загрузок | 30/мин на клиента (`429`) | при `429` подождите `Retry-After` |
| Параллельные сканы | 5 «в работе» | дождитесь завершения |
| Динамика | объект ≤ лимита песочницы (≈6 ГиБ) | для ТБ-моделей — только статика + сэмплы (см. §3) |
| Квоты тенанта | байты/сутки, RPS, параллелизм | при `403`/`429` — уточните квоту у админа |

### 1.4 Требования к самим данным

- **LLM**: предпочтителен **GGUF** (указывайте квантизацию: `Q4_K_M`, `Q5_K_M`, `Q8_0`, `F16`);
  для запуска нужен **движок инференса** из уже скачанных (система не даст скачать LLM без него).
- **Архивы**: допускаются обычные zip/tar, включая вложенные; «бомбы»/небезопасные пути
  (`../`, абсолютные) система помечает и **не раскрывает** за пределами бюджета.
- **Образы движков**: только **по digest** и из внутреннего реестра (подпись/SBOM проверяются
  admission-политикой). Тег (`:latest`) как идентификатор не принимается.
- **Секреты**: токены/ключи не передавайте в именах файлов и в метаданных; HF-токен вводите в
  отдельной форме («Модель с HF») — он сохраняется в защищённом хранилище и показывается только
  маской вида `hf_***`.

## 2. Сценарии проверки (пошагово)

### S1. Обычная модель (не-LLM): быстрая проверка
1. UI → «Загрузки → Модели (кроме LLM)» → выберите файл → «Загрузить».
2. Дождитесь появления записи в таблице; состояние: `queued → running → done`.
3. Откройте карточку артефакта: смотрите **вердикт**, **severity/risk**, список **находок**
   (`L1/L2/L3`), **покрытие**.
4. Если вердикт `Inconclusive` — см. §3.3 (это **не** «безопасно»).

### S2. LLM: проверка с запуском инференса
1. Заранее («Движки инференса») убедитесь, что нужный **движок скачан** (по digest). Если нет —
   импортируйте его (ссылка/OCI-архив).
   > HF подключён **реально**: egress подов ограничен точечным allowlist к Hugging Face и его CDN
   > (только TCP/443; см. `deploy/ingress/33-egress-hf.yaml`), публичные модели качаются без токена.
   > Для приватных репозиториев сохраните **HF-токен** (кнопка «Сохранить токен», в UI показывается
   > только маска `hf_***`). Токен хранится зашифрованным per-tenant и применяется к поиску и загрузке;
   > очистить сохранённый токен — сохранить пустое значение.
2. «Загрузки → Модель с HF» (или «Локальные LLM» для своего файла):
   - при необходимости сохраните **HF-токен** (кнопка «Сохранить токен»);
   - в **поиске** задайте критерии (`name/query`, `type`, `quantization`), выберите модель из списка;
   - **выберите движок** (обязательно) → нажмите загрузку.
3. Система скачает модель (фоном, с докачкой — окно можно закрыть), создаст **bundle**
   (модель + образ движка + версии) и запустит тест: инференс + прогон набора вопросов.
4. В карточке смотрите: вердикт bundle, **поведение** (события `LLM-B-*`), **ответы по вопросам**,
   метрики (`pass_rate`, `safety_fail`), покрытие, аттестацию.

### S3. Архив моделей (все форматы)
1. «Модели (кроме LLM)» → загрузите архив (`fmt=zip`/`tar`).
2. Система читает оглавление, обходит членов (в т.ч. вложенные архивы) в рамках бюджетов.
3. В результате: агрегированный вердикт по архиву + перечень членов с их форматами/находками;
   пропущенные члены помечены причиной (бюджет/размер/«бомба»).

### S4. Движок не подошёл: смена и перезапуск теста
1. Если при старте инференса видно, что движок не запускается/не подходит — откройте
   «Загрузки → Локальные LLM → Перепривязка движка».
2. Укажите `model sha256` и **другой движок** из скачанных → «Сменить движок и перезапустить».
3. Создаётся **новый bundle** для той же модели (модель повторно не загружается); история
   сохраняется (видно в `GET /bundles?model=<sha>`).

### S5. Автоматическая проверка в CI (gate)
- CI запрашивает решение по паре (**образ движка**, **модель**):
  `GET /gate?image=<…@sha256:…>&model=<sha256>` (через сервис integrations).
- Ответ: `decision ∈ {allow, block, quarantine}` + `bundle_id` + аттестация. Пайплайн
  блокируется на `block` и помечается на `quarantine`.

### BTF-ядро Kata и in-guest eBPF-сенсор (B1)

```bash
MLSCAN_NODE_SSH=user@node bash deploy/v3/sandbox/kata-btf/install.sh          # BTF-ядро (обратимо)
kubectl apply -f deploy/v3/sandbox/kata-btf/30-allow-ebpf-agent.yaml           # политики (privileged+guard)
kubectl -n mlscan-testing set env deploy/mlscan-testing SANDBOX_EBPF=1 LLM_TEST_EBPF=1
kubectl -n mlscan-sandbox create configmap mlscan-ebpf-agent \
  --from-file=ebpf_agent.py=deploy/v3/sandbox/kata-btf/ebpf_agent.py
```

ВНИМАНИЕ (осознанное решение): namespace `mlscan-sandbox` работает в PodSecurity `privileged`
(`restricted`/`baseline` не позволяют добавить `BPF`/`PERFMON`), поэтому безопасность namespace
обеспечивают только Kyverno-политики (digest-образ, non-root кроме `ebpf-agent`, drop ALL, RO-FS,
seccomp, запрет `privileged`/`host*`/опасных caps). Сенсор `ebpf-agent` — root **внутри гостевой ВМ**
Kata (non-root не может загрузить eBPF: `CapEff=0` → EPERM). Проверка: `tests/e2e/sandbox_ebpf_e2e.sh`
(скан → `LLM-B-01` в `/llm/events`), `tests/e2e/llm_ebpf_inference_e2e.sh` (инференс → `LLM-B-01`).

### BTF-ядро Kata для in-guest eBPF (B1)

```bash
MLSCAN_NODE_SSH=user@node bash deploy/v3/sandbox/kata-btf/install.sh
```

Переключает ядро Kata-песочницы на BTF-вариант (`vmlinux-debug.container`) — **без рестарта**

```bash

curl -sX POST -H "X-API-Key: <adm>" -H 'Content-Type: application/json' \
     -d '{"tenant":"operator","daily_bytes":10737418240}' http://<testing>/hf/quota
```

### Аудит решений CI-gate (N3)

Каждое решение `/gate` подписано и записано в журнал:

```bash
curl -sH "X-API-Key: <adm>" 'http://<testing>/gate/decisions?model=<sha256>&limit=20' | python3 -m json.tool
```

Поля: `source` (`bundle-verdict` — по вердикту bundle, `bundle-no-verdict` — тест не прогнан,

`decision`, `attestation_digest`, `signature`. Журнал append-only: изменить/удалить запись нельзя.

### Запуск теста bundle из UI (N2)

«Загрузки → Тест bundle»: укажите `bundle_id` (или sha256 модели — возьмётся первый подходящий bundle)

## 3. Интерпретация результатов

### 3.1 Вердикты (что означает каждый)

| Вердикт | Значение | Как трактовать |
|---------|----------|----------------|
| **Safe** | все модули отработали, находок нет/незначительные | можно использовать (при полном покрытии) |
| **Needs review** | есть находки среднего уровня | требуется ручной разбор до использования |
| **Dangerous** | high/critical-находки без жёсткой динамики **или** жёсткие динамические сигналы | не использовать без ручного подтверждения |
| **Malicious** | high/critical **и** опасная динамика (сеть/процессы/exec/dlopen/запись/таймаут) | **блокировать** |
| **Inconclusive** | полного покрытия не получилось, а доказательств опасности нет | **не «безопасно»**: нужна отдельная проверка/условия |

### 3.2 Severity, risk, находки

- Уровни: `critical > high > medium > low > info`; **score** считается от тяжести находок
  (`risk_score = min(10, top + 0.2·остальные)`), поле `max_severity`.
- Идентификаторы находок по группам: `A-*` (pickle/десериализация), `F-*` (форматы/структура),
  `EXEC-*`, `INJ-*`, `SEC-*`, `FMT-*` (архивы/границы), `BD-*` (аномальные значения тензоров),
  `IMG-*` (образы), `LLM-B-*` (поведение инференса: shell/egress/honeypot/mem-exec/модуль).
- «Жёсткие» динамические сигналы: попытки сети, запуск процессов/команд, исполнение в памяти,
  загрузка нативных библиотек, запись файлов, таймаут.

### 3.3 Покрытие (coverage) и `Inconclusive`

Покрытие показывает, **какие модули реально отработали**: `static`, `dynamic`, `behavior`.
Модуль «выполнен» только если он отработал без ошибок (динамика — запустилась песочница И модель
загрузилась). Правило: если что-то не удалось, система **не пишет `Safe`**, а возвращает
`Inconclusive` с перечнем непроверенного (исключение: частичные данные уже доказывают опасность —
тогда вердикт опасности сохраняется, а неполнота указывается в причине).

Что делать при `Inconclusive`:
1. прочитать **причину** (`reason`) и модули с `ok=false`;
2. если не хватило библиотеки/размера — использовать иной тип проверки (статика по индексу/сэмплы);
3. для ТБ-моделей это ожидаемо: полная динамика не запускается (лимиты песочницы) — в карточке
   будет `dynamic=skipped`; опирайтесь на статику по индексу и **сэмплированные** проверки;
4. зафиксировать решение в протоколе (§4 приложения).

### 3.4 Решение политики и действия

Поверх вердикта работает Policy Engine: `action ∈ {allow, quarantine, block}` и, при необходимости,
свой вердикт/причина. Значение по умолчанию — `quarantine` («Недостаточно данных»). Политику
настраивает администратор (страница `/policy`); оператор видит итог в поле `action`/`policy_action`.

### 3.5 Доказательства (evidence) и аттестация

- Каждое решение попадает в **append-only evidence** с HMAC-подписью; проверка: `GET
  /api/evidence/verify` (аналитика) → `ok/signed/entries`.
- Для пары (образ, модель) формируется **подписанная аттестация** (digest, версии, вердикт);
  решение доступно через `GET /gate?image&model`, воспроизводимо при повторном прогоне того же bundle.

### 3.6 Поведение LLM-инференса (что считается опасным)

События `LLM-B-*`: запуск shell/интерпретатора (`LLM-B-01`), внешние сетевые соединения
(`LLM-B-02`; локальные/sinkhole — разрешены), чтение honeypot-секретов (`LLM-B-03`), исполняемая
память (`LLM-B-04`), загрузка модулей (`LLM-B-05`). Любое из них при инференсе — сильный сигнал.

## 4. Ограничения, влияющие на выводы

- **Сэмплирование**: крупные модели/архивы проверяются выборочно (индекс + сэмплы/члены/срезы с
  бюджетами) — покрытие отражается явно; отсутствие находок при неполном покрытии ⇒ `Inconclusive`.
- **Дизайн-лимиты**: см. `14-limitations.md` (лимиты архивов, отсутствие полной динамики для ТБ,
  MIG не поддерживается текущими GPU и т.п.).
- **Иммутабельность**: вердикт привязан к bundle (образ+модель+версии правил); после обновления
  правил результат может измениться — это **новый** bundle, а не ошибка.

## 5. Приложения

### 5.1 API-шпаргалка (основное)

```
# обычная загрузка
POST /scans/upload?name=&fmt=            (тело: файл; шаг 1 МиБ)
GET  /scans/<id>                          вердикт, находки, покрытие
# большие файлы (прямо в S3)
POST /uploads/initiate {name,fmt,sha256,size}          → presigned-части
GET  /uploads/<id>/parts                               → загруженные части (resume)
POST /scans/complete {upload_id, parts:[{part_number,etag}]}
# LLM/HF
POST /hf/search {query,type,vendor,quantization}       → список моделей
POST /hf/token {token}                                 → сохранить HF-токен (маска)
POST /hf/downloads {repo_id,quantization,engine_image} → фоновая загрузка (LLM: движок обязателен)
POST /bundles {model_sha256,engine_image,...}          → bundle
GET  /bundles?model=<sha256>                           → история bundle
POST /bundles/<id>/rebind {engine_image}               → новый bundle (перезапуск)
GET  /gate?image=<…@sha256:…>&model=<sha256>           → allow|block|quarantine
# служебное
GET  /images/list        POST /images/import           → движки (импорт по digest)
GET  /v3/metrics         GET  /v3/slo                  → метрики/SLO
GET  /quality            POST /retest                  → качество на golden-наборе (ops)
GET  /api/evidence/verify                              → целостность evidence (аналитика)
```

### 5.2 Коды ошибок (что делать)

| Код | Причина | Действие |
|-----|---------|----------|
| `401` | нет/истёк ключ или сессия | получить ключ/перелогиниться |
| `403` | нет роли или превышена квота тенанта | уточнить у админа |
| `413` | файл больше `MAX_UPLOAD` | согласовать лимит/прямая загрузка в S3 |
| `429` | частота/суточная квота | подождать `Retry-After`, уменьшить темп |
| `400 engine_image обязателен…` | LLM без выбранного движка | выбрать скачанный движок |
| `409/`ошибка S3`` | временный сбой хранилища | повторить; при повторе — к админу |

### 5.3 Чек-лист оператора перед использованием модели

- [ ] понятен вид артефакта и формат; для LLM подтверждена квантизация и выбран движок;
- [ ] загрузка завершилась, `sha256`/`size` совпадают с исходником;
- [ ] покрытие полное (или причина `Inconclusive` понятна и зафиксирована);
- [ ] вердикт и `action` прочитаны; при `quarantine`/`block` — не использовать без разбора;
- [ ] для CI — проверена пара (образ, модель) через `/gate`, есть аттестация;
- [ ] решение и обоснование внесены в протокол.

### 5.4 Протокол проверки (шаблон)

```
Модель: <имя>, формат: <fmt>, размер: <bytes>, sha256: <hex>
Проверка: bundle <id>, движок: <…@sha256:…>, версии: prompt-set=<…>, detectors=<…>, policy=<…>
Результат: вердикт=<…>, action=<…>, risk_score=<…>, max_severity=<…>
Покрытие: static=<ok>, dynamic=<ok|skipped: причина>, behavior=<ok|…>
Ключевые находки: <check_id> (<severity>): <кратко>; события LLM-B: <…>
Evidence: verify=<ok>, аттестация digest=<…>
Решение оператора: <допустить/карантин/блок>, обоснование: <…>, дата/подпись: <…>
```
