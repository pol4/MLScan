# DR runbook (v3, P8)

Цели: **RPO ≤ 15 мин**, **RTO ≤ 1 ч** (см. `Arch_v3/01-requirements.md`).

## Что резервируется
- **Data-plane (S3)**: RF≥2/erasure coding, multi-site репликация (async) или backup в внешний S3.
- **PostgreSQL**: HA-репликация + WAL-стриминг; периодические дампы (проверка восстановления).
- **Registry образов**: репликация реестра/бакета; attestations — WORM.
- **Evidence**: append-only + HMAC + WORM-анкор головы (внешний object-lock/TSA).

## Шаги восстановления (сайт/узел недоступен)
1. Оценить масштаб (узел S3 / control / сайт) → выбрать режим failover.
2. Data-plane: переключить клиентов на выжившие узлы/сайт; дождаться ре-репликации.
3. Control-plane: поднять реплики в другом домене; leader-lock переизберётся автоматически.
4. PostgreSQL: promote-реплика (WAL) или restore из дампа (RPO по лагу/бэкапу).
5. Registry: переключиться на реплику; проверить доступность образов по digest.
6. Проверить evidence-цепочку (`verify`) и анкор; при расхождении — карантин и ручной разбор.
7. Smoke: загрузка объекта, статика, LLM-бандл, `/v3/metrics`, `/v3/slo`.

## Ограничения текущего стенда
- **Одиночный узел**: реальный HA/DR между физическими узлами/сайтами недостижим; проверяется
  single-writer (advisory-lock) и отсутствие потери данных при перезапусках. Полноценные chaos/DR-drill
  — на целевом железе (multi-node/multi-site), см. `Arch_v3/15-implementation-plan.md` (P8).
