# 14. Анализ ИБ архитектуры и кода MLScan + план доработок

Документ отвечает на два вопроса:

1. **Может ли MLScan стать плацдармом для атаки на другие системы** (кластер, соседние проекты,
   внешние хосты) — то есть используется как средство нападения, а не анализа.
2. **Может ли MLScan перестать быть достоверным источником** сведений о безопасности артефактов —
   то есть выдать ложный «Safe», подделать находки/доказательства/политику или деградировать так,
   что его выводам нельзя доверять.

В конце — **план доработок** (P0 — немедленно, P1 — ближайший спринт, P2 — плановые).
Фактическая архитектура и границы доверия — [`07-implemented-architecture.md`](./07-implemented-architecture.md),
изоляция — [`03-isolation.md`](./03-isolation.md), уровни развёртывания — [`13-deployment-plan.md`](./13-deployment-plan.md).

---

## 1. Границы доверия (кратко)

| Зона | Что доверено | Что недоверенно |
|------|--------------|-----------------|
| Песочница (`mlscan-sandbox`, Kata microVM) | код harness (наш) | **артефакт и всё, что он исполняет** |
| Доверенная зона (`testing`, `analytics`, `ops`, `integrations`, `data`) | код сервисов, БД, S3 | **входные данные** (артефакты, их метаданные, названия, отчёты) |
| Общий кластер | `kata`, Istio, registry, `kube-*` | наши namespace и наши объекты |
| Внешняя среда (CI, аналитик, браузер) | браузер, API-клиенты | сеть до ingress |

Инварианты, которые обязана обеспечивать система:

* **I1.** Артефакт не исполняется в доверенной зоне.
* **I2.** Песочница не может инициировать сетевые соединения к чужим системам (кроме sinkhole/DNS).
* **I3.** Вердикт и находки отражают то, что реально наблюдалось; неполнота отражается как
  `Inconclusive`, а не как `Safe`.
* **I4.** Доказательства и решения нельзя изменить незаметно.
* **I5.** Компрометация одного сервиса не даёт управления кластером и не влияет на чужие проекты.

## 2. Сценарии атак

### A. MLScan как плацдарм

| # | Сценарий | Механика | Что уже мешает | Остаточный риск |
|---|----------|----------|----------------|-----------------|
| A1 | **DNS-туннель / C2 из песочницы** | payload обращается к внешним именам через `kube-dns` (egress на 53 разрешён) и кодирует данные в DNS-запросах | исходящие TCP/UDP наружу запрещены (deny-by-default) | средний: DNS разрешён всем и резолвит внешние имена |
| A2 | **Перегрузка кластера сканами** | массовая загрузка артефактов → шторм sandbox-Job (CPU/RAM/диск узла), влияет на соседние проекты | лимиты на Job, `ephemeral-storage`, PDB у сервисов | высокий: нет квот/лимитов на namespace и на клиента |
| A3 | **Перегрузка доверенной зоны артефактом** | zip-бомба (1 КБ deflate → ГБ), тысячи находок, гигантский JSON | детектор bomb (`FMT-04`), ограничение чтения файла 64 МБ | средний: разжатие членов zip не ограничено (см. F-B3) |
| A4 | **Подмена образа песочницы** | у нашего образа **тег, а не digest**; реестр без аутентификации внутри кластера → подмена `mlscan-sandbox:v4` даёт исполняемый код в песочнице (и возможность подделать результат) | kata, read-only FS, сетевой запрет внутри | высокий: результаты становятся недоверенными |
| A5 | **Lateral movement из доверенной зоны** | egress платформенных namespace разрешён на **весь кластерный CIDR** и порты 443/8080/8090/3900/5432 → компромисс сервиса = доступ к API-серверу и к чужим HTTPS-сервисам | нет | высокий |
| A6 | **Kubernetes API из сервиса тестирования** | SA `mlscan-testing` может **создавать Job в `mlscan-sandbox`** → произвольный образ/команда → исполнение кода в кластере и потребление ресурсов | PSA restricted, no token в песочнице, нет секретов в ns песочницы | средний |
| A7 | **Sinkhole как «внутренний сервис»** | payload «атакует» sinkhole (единственный разрешённый адрес) | sinkhole только принимает, изолирован | низкий |

### B. Компрометация доверенной зоны недоверенным вводом

| # | Сценарий | Механика | Остаточный риск |
|---|----------|----------|-----------------|
| B1 | **L1-парсинг артефакта** | статика крутится в сервисе тестирования: зип/тар/XML/YAML/ONNX/GGUF/HDF5/Protobuf-подобные данные | низкий/средний: наш код на Python (без памяти), но разбор не фаззился |
| B2 | **Path traversal по имени артефакта** | `name` из `?name=` | **закрыт**: `os.path.basename()` на загрузке и на отдаче |
| B3 | **Бомба внутри zip** | `zf.read(member)` без ограничения на **размер разжатого** члена (лимит 8 МБ только для вложенных архивов) | средний: OOM сервиса (DoS), не RCE |
| B4 | **Взрыв числа находок** | pickle с тысячами глобалов → десятки тысяч находок → раздувание PG/JSON/UI | средний: нет лимита на число/размер находок |
| B5 | **ReDoS в наших регулярках** | regex по `PIPE_TO_SHELL`, `CSV_FORMULA`, JJinja/шаблонам | низкий: квантификаторы ограничены (`{0,300}`), текст ограничен 64 МБ |

### C. Недостоверность MLScan как источника истины

| # | Сценарий | Механика | Остаточный риск |
|---|----------|----------|-----------------|
| C1 | **Подмена результата песочницы** | сервис разбирает **последнюю** строку `MLSCAN_RESULT_JSON:` из stdout контейнера; **нонса нет**, результат не подписан и не сверяется с итогом процесса → payload печатает «чистый» JSON (например, форкнутый процесс после выхода harness) | **критический**: ложный `Safe`/скрытие находок |
| C2 | **Тихая деградация покрытия** | payload «глушит» динамику (убивает процесс, забивает stdout, зацикливается) | частично закрыт: `Inconclusive` + баннер неполной проверки; но метрик/алертов на долю `Inconclusive` нет |
| C3 | **Подмена политики/кода** | `mlscan-policy`, `mlscan-harness`, `mlscan-poc-lib`, `mlscan-formats`, `mlscan-i18n` — обычные ConfigMap без подписи/контроля целостности: правка = подмена правил принятия решений и логики анализа | высокий (при доступе к ns) |
| C4 | **Подмена доказательств** | evidence — append-only (файл + триггеры PG), но **цепочка не подписана**; при доступе к PVC/БД её можно пересобрать целиком, а `attest.sh` (HMAC) запускается вручную | средний |
| C5 | **Статический ключ сервис-сервис** | `analytics → testing` использует общий `INTERNAL_KEY` (роль `service`); ключи из Secret, **без срока жизни/ротации** и без mTLS; утечка = возможность отдавать ложные данные/имперсонировать сервис | высокий |
| C6 | **Отравление реестра/gate** | реестр в integrations (`sha256 → entry`) наполняется при сканировании; `S3` не перезаписывается (dedup по `sha256`) | низкий: ключ — содержимое, а не имя |
| C7 | **Гонка вердикта** | один `scan_id` — один артефакт; повторная загрузка того же sha переиспользует объект, но создаёт новый скан | низкий |
| C8 | **Подмена UI-данных** | XSS через поля артефакта (имя, находки, ошибки) | закрыт: поля экранируются (`_esc`), cookie `HttpOnly`+`SameSite=Lax` |

### D. Доступность и эксплуатация

| # | Сценарий | Механика | Остаточный риск |
|---|----------|----------|-----------------|
| D1 | **DoS на API/UI** | нет rate limit: поток загрузок/запросов к `/scans`, `/api/overview` (дашборд опрашивает каждые 5 с) | средний |
| D2 | **Зависимость от БД** | `analytics`/`testing` синхронно пишут в PG; при недоступности PG деградируют (файлы остаются) | низкий: есть файловый фолбэк |
| D3 | **Таймауты вместо отказа** | попытки сети из песочницы «висят» до таймаута (DROP). Это не атака, но замедляет сканы (см. P0-4) | низкий |

## 3. Что уже сделано хорошо (сохранить)

* **Изоляция**: Kata microVM на артефакт, `--network none`-эквивалент (default-deny + sinkhole/DNS),
  read-only rootfs, drop ALL, seccomp, лимиты, honeypot-файлы, sinkhole-адреса, уничтожение среды.
* **Артефакт не в доверенной зоне**: песочница скачивает файл у сервиса по одноразовому токену,
  привязанному к `scan_id`; сеть песочницы не расширяется.
* **Честность вердикта**: неполнота покрытия → `Inconclusive` + перечень непроверенного (в сервисе,
  в аналитике и в UI/отчётах), исторические записи пересчитываются.
* **Целостность данных**: evidence append-only (файл + триггеры БД), hash-chain, дедупликация по
  `sha256` без перезаписи объектов.
* **Валидация входа**: `scan_id` — только `[0-9a-f]{6,64}`; `name` — `basename` на загрузке и отдаче.
* **Аутентификация/сессии**: API-ключи и пользователи в БД (PBKDF2, 200k), сессии — HMAC-подписанные,
  12 ч, `HttpOnly`, `SameSite=Lax`, `Max-Age`; роли `admin`/`ci-reader`/`service`; аудит в `audit_log`.
* **UI**: экранирование всех полей; глобальный язык с настройкой в БД; никакого HTML от артефакта.
* **Эксплуатация**: метрики, качество (TPR/FPR), retention/TTL, карантин, backup+restore, PDB.

## 4. План доработок

### P0 — немедленно (закрывают прямую недостоверность и плацдарм)

| ID | Задача | Реализация (где) | Критерий приёмки |
|----|--------|------------------|------------------|
| P0-1 | **Нонс результата + сверка** | `poc/mlscan_poc.py` (harness печатает `MLSCAN_RESULT_JSON:<nonce>:{…}`), `deploy/stage2/service/mlscan_testing.py` (генерирует nonce на скан, передаёт в Job через env, ищет **только** свою строку, сверяет с `MLSCAN_SUMMARY:<nonce>` и с exit code/статусом Job) | payload с фальшивым `MLSCAN_RESULT_JSON` без нонса **не влияет** на вердикт; тест `tests/vulnerabilities` дополнен образцом-спуфером |
| P0-2 | **Digest вместо тега для образа песочницы** | `SANDBOX_IMAGE` принимает `image@sha256:…`; `deploy/stage2/30-service.yaml` + `install.sh` пишут digest после сборки; Job использует digest, `imagePullPolicy: IfNotPresent` | смена тега в реестре не меняет исполняемый код; verify проверяет digest |
| P0-3 | **Ограничение разжатия в доверенной зоне** | `poc/formats.py`: читать члены архивов только с лимитом на **разжатый** размер (напр. 32 МБ) и на суммарный объём; считать отношение сжатия до чтения; лимит числа членов | zip-бомба (`FMT-04`) не приводит к росту RSS сервиса; скрипт-тест с бомбой 1 КБ→1 ГБ |
| P0-4 | **Мгновенный отказ сети из песочницы** | Calico `GlobalNetworkPolicy` для `mlscan-sandbox`: `Allow` (DNS-резолвер, sinkhole, testing:8090) → `Reject` вместо неявного DROP; замер времени отказа | сетевой вызов из payload завершается `ConnectionRefused` < 1 с (не таймаут); скан-тест с сетевым payload ускоряется |
| P0-5 | **Лимиты и квоты namespace/клиента** | `ResourceQuota`+`LimitRange` для `mlscan-sandbox`/`mlscan-data`; ограничение числа одновременных Job; простейший rate limit на `/scans/upload` по ключу/IP | шторм из N загрузок не выводит узел из строя; при превышении — `429`/`Inconclusive` без падения |
| P0-6 | **Защита конфигурации от подмены** | RBAC: писать ConfigMap сервисов может только `admin`-роль (ClusterRole/Policy); при старте сервисы сверяют контрольные суммы своих CM (`mlscan-poc-lib`, `mlscan-formats`, `mlscan-harness`, `mlscan-policy`) с ожидаемыми в подписанной аннотации/Secret | изменение CM без обновления эталона → сервис не стартует/пишет critical-алерт |

### P1 — ближайший спринт (уменьшают площадь атаки и повышают доверие)

| ID | Задача | Реализация | Критерий приёмки |
|----|--------|-----------|------------------|
| P1-1 | **Сужение egress платформенных namespace** | `deploy/ingress/30-*.yaml`: вместо всего кластерного CIDR — только `mlscan-data`, sinkhole-адрес (для testing не нужен), DNS-резолвер, адрес K8s API; остальное — `Reject` | из testing/analytics недоступны чужие сервисы и произвольные 443/8080 в кластере |
| P1-2 | **DNS-политика песочницы** | пропускать DNS только на **наш** резолвер (или NodeLocalDNS-стаб), который отдаёт `NXDOMAIN` для внешних имён; либо статические записи для testing/sinkhole | payload не резолвит внешние домены → DNS-туннель невозможен |
| P1-3 | **Ограничение прав SA тестирования** | Kyverno/ValidatingAdmissionPolicy: Job в `mlscan-sandbox` только с образом нашего digest, обязательный securityContext, запрет hostPath/hostNetwork/privileged; отдельный SA только для создания Job | любой другой Job в ns песочницы отклоняется admission-webhook'ом |
| P1-4 | **Срок жизни и ротация ключей** | `authz`: `expires_at` для API-ключей (таблица `api_keys`), ротация `INTERNAL_KEY`/`SESSION_SECRET` процедурой `keys.sh`; раздельные ключи для analytics↔testing и ops↔аналитика | истёкший ключ → 401; ротация без простоя; в аудите видны события ротации |
| P1-5 | **Подпись доказательств и политики** | HMAC-цепочка evidence существующим `attest.sh` (ключ — вне БД/PVC), автоматический запуск по cron и при `/retest`; подпись `policy.json` и проверка при загрузке | изменение строки evidence или policy без ключа ломает проверку; UI показывает статус attestation |
| P1-6 | **Метрики целостности и алерты** | `ops`: доля `Inconclusive`, доля неполной динамики, ошибки разбора, расхождение summary/result, отказы сети в песочнице → `/metrics` + `/alerts` | падение доли полного покрытия или рост подмен/ошибок вызывает алерт |
| P1-7 | **Лимит находок и объёма JSON** | cap на число находок (напр. 500 с записью «усечено»), cap на размер evidence-записи; усечение с пометкой в вердикте | «взрыв находок» не раздувает БД/UI и не искажает вердикт молча |
| P1-8 | **Аудит действий с нашими объектами** | включить аудит K8s (или логировать изменения CM/Secret нашими сервисами), SIEM-экспорт изменений policy/harness | все изменения правил и кода анализа видимы в SIEM |

### P2 — плановые (устойчивость и доверие на длинной дистанции)

| ID | Задача | Комментарий |
|----|--------|-------------|
| P2-1 | **Fuzzing парсеров** (zip/tar/XML/YAML/ONNX/GGUF/HDF5/safetensors) в CI + корпус враждебных образцов на каждый фикс | превращает «разбор не фаззился» в проверяемое свойство |
| P2-2 | **Подпись и SBOM образа песочницы** (cosign/syft), проверка подписи в admission | продолжение P0-2 на уровне цепочки поставки; pinned-хэши pip-зависимостей |
| P2-3 | **mTLS/OIDC** между сервисами и для операторов (вне плана 13 — теперь как отдельный трек) | убирает доверие к статическому `INTERNAL_KEY` |
| P2-4 | **WORM/внешняя копия evidence** (S3 object-lock, ежедневная выгрузка + офлайн-проверка) | защита от «пересборки» цепочки при доступе к PVC/БД |
| P2-5 | **Изоляция данных по пользователю/команде** (если появится мультитенантность) | сейчас single-tenant; при росте — разграничение видимости сканов |
| P2-6 | **Регулярный red-team** (расширение `stage5/40-redteam-job.yaml`: попытки подмены результата, DNS-туннеля, перегрузки) | превращает сценарии из §2 в автотесты |
| P2-7 | **Лимиты на стороне ingress** (Istio rate limit/local ratelimit) | защита UI/API от внешнего флуда |

### Порядок и эффект

1. **P0-1, P0-2, P0-6** — закрывают прямую подмену вердикта/логики (главный риск для достоверности).
2. **P0-3, P0-4, P0-5** — убирают DoS доверенной зоны и перегрузку кластера (риск для соседних проектов).
3. **P1-1…P1-4** — сокращают площадь атаки и lateral movement.
4. **P1-5…P1-8, P2-\*** — доказуемость, наблюдаемость и цепочка поставки.

## 5. Приложение: как проверять после доработок

* **Спуфер результата**: образец, печатающий поддельный `MLSCAN_RESULT_JSON:` — вердикт не должен
  становиться «чистым» (P0-1).
* **Zip-бомба**: 1 КБ → 1 ГБ; RSS сервиса не растёт выше лимита, статус `Inconclusive`/находка `FMT-04` (P0-3).
* **Сетевой payload**: время отказа < 1 с, событие фиксируется sinkhole/Falco (P0-4).
* **Шторм загрузок**: квота/`429`, узел и соседние проекты не деградируют (P0-5).
* **Правка ConfigMap**: сервис не стартует или алертит (P0-6).
* **Смена тега образа в реестре**: результат не меняется (P0-2).
* **Истечение ключа**: `401`; ротация без простоя (P1-4).
* **Attestation**: изменение строки evidence → проверка падает (P1-5).
