# Чеклист потенциальных опасностей моделей ML в формате pickle

Документ описывает исчерпывающий перечень рисков, связанных с приёмом, хранением,
загрузкой и применением ML-моделей, поставляемых в формате pickle (`.pkl`, `.pickle`,
`.joblib`, `.pt`, `.pth`, `.bin`, `.npy/.npz` с `allow_pickle=True`, `dill`,
`cloudpickle` и их производных).

Формат pickle способен сериализовать **произвольные Python-объекты и вызывать
произвольный код** при десериализации. Поэтому модель в формате pickle — это не
«данные», а **исполняемая программа** с полным набором связанных рисков.

Категории чеклиста:
- **A. Риски десериализации (execution-time)** — код, исполняемый при `load`/`unpickle`.
- **B. Форматы-обёртки и векторы доставки** — как маскируется опасный payload.
- **C. Риски уровня модели (модель как алгоритм)** — вредоносность/дефекты самой модели.
- **D. Целостность, происхождение и цепочка поставки (supply chain)**.
- **E. Раскрытие информации (информационные утечки)**.
- **F. Неконтролируемое поведение при загрузке и инференсе**.
- **G. Риски окружения исполнения и сопутствующих артефактов**.
- **H. Риски инфраструктуры сканера и процесса проверки**.
- **I. Юридические, комплаенс и репутационные риски**.

Для каждого пункта указываются: идентификатор, описание, механизм/вектор,
пример, наблюдаемые признаки (observables), и уровень серьёзности.

Шкала серьёзности: **C** — критическая, **H** — высокая, **M** — средняя, **L** — низкая.

## A. Риски десериализации (execution-time)

| ID | Риск | Механизм | Наблюдаемые признаки | Severity |
|----|------|----------|----------------------|----------|
| A-01 | Произвольное исполнение кода (RCE) при `pickle.load` | Opcodes `REDUCE`, `GLOBAL`/`STACK_GLOBAL`, `BUILD` вызывают произвольные callable | Подозрительные глобалы (`os.system`, `subprocess`, `eval`, `exec`, `builtins`, `getattr`) | C |
| A-02 | Исполнение через `__reduce__` | Объект определяет `__reduce__`/`__reduce_ex__`, возвращающий `(callable, args)` | Кастомные классы в pickle с подозрительным callable | C |
| A-03 | Исполнение через `__setstate__` / `BUILD` | `BUILD` вызывает восстановление состояния объекта | Классы с `__setstate__`, читающим файлы/сеть | H |
| A-04 | Shadowed `find_class` (перехват загрузки) | Переопределение `pickle.Unpickler.find_class` расширяет доступные имена | Нестандартные загрузчики, monkey-patching | H |
| A-05 | Динамическая компиляция кода во время load | `compile`, `types.FunctionType`, `marshal.loads`, `exec` | Наличие байткода/marshal/`code`-объектов в payload | C |
| A-06 | Обфускация и упаковка payload | Base64/zlib/marshal внутри pickle, многослойные pickle | Высокая энтропия строк, blob-поля | H |
| A-07 | Вложенные/рекурсивные pickle | pickle внутри pickle, скрытый второй payload | Вложенные `PROTO`, повторные `load` | H |
| A-08 | Использование устаревших/опасных opcodes | `INST`, `OBJ`, `GLOBAL`, `EXT*` | Редкие/устаревшие opcodes | M |
| A-09 | `persistent_load` с побочными эффектами | Загрузка внешних данных по ключу | `persistent_id`/`persistent_load` в кастомных Unpickler | M |
| A-10 | Side-channel через pickle `PROTO`/`MEMO` | Извлечение данных через порядок opcodes | Аномальная структура потока | L |
| A-11 | RCE через `dill`/`cloudpickle` | Сериализуют функции/замыкания целиком | Полные `FunctionType`-объекты, исходники | C |
| A-12 | RCE через `joblib` | joblib использует pickle + numpy | Вредоносные callable в joblib-контейнере | C |
| A-13 | RCE через `torch.load` (legacy) | PyTorch использует pickle; `weights_only=False` | `_rebuild_*`, `torch.storage`, `torch.Size`-трюки | C |
| A-14 | Обход `weights_only=True` | Исторические уязвимости allowlist-ов | Известные CVE PyTorch (напр. CVE-2025-32434) | C |
| A-15 | RCE через Keras Lambda layers | SavedModel/H5 с произвольным `Lambda` | `lambda`-функции, Python-код в конфиге слоя | C |
| A-16 | RCE через numpy object-array | `.npy/.npz` с `allow_pickle=True` | Скалярные object-массивы с callable | C |
| A-17 | `trust_remote_code=True` (HF) | Загрузка и исполнение репозиторного кода | `auto_map`, custom `modeling_*.py` | C |
| A-18 | Исполнение кода в кастомных ops ONNX | Custom operators / Python runtime | Нестандартные операторы, внешние библиотеки | H |

## Ключевой вывод для архитектуры

Опасность pickle-модели выходит далеко за пределы «выполнить вредоносный код при загрузке».
Полный охват требует трёх независимых контуров проверки:

1. **Статический** — анализ артефакта без исполнения (opcodes, AST, allowlist, метаданные, целостность).
2. **Динамический** — исполнение в герметичной песочнице с полным наблюдением (syscalls, сеть, файлы, ресурсы).
3. **Поведенческий** — тестирование уже работающей модели на backdoor, утечки и дефекты надёжности.

Эти три контура ложатся на три архитектурные компоненты (Песочница, Сервис тестирования,
Аналитический движок) — см. `05-architecture.md` и `Concept.md`.
